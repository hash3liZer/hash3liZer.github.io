<h2 id="introduction"><a href="#introduction">Introduction</a></h2>
<p>So, way back in <strong>2019</strong> i wrote a post titled <em>"MITM: Bypassing 2FA with Advanced Level Phishing Framework"</em>. It's one of the oldest articles i have and it has aged terribly. Freenom doesn't hand out free domains anymore, <code>go get</code> isn't how you install anything these days, and Evilginx itself got a complete rewrite. People kept messaging me that the old commands just don't work. Fair enough, this is the 2026 do-over.</p>
<p>This time i actually spun up a fresh server and built the latest <strong>Evilginx 3.3.0</strong> from source, running the whole thing end to end while writing this. So every terminal view below is real output from a live box, not something i typed from memory. I've rendered those outputs as little terminal windows so you can see exactly what each step looks like.</p>
<blockquote>
<p>⚠️ Quick disclaimer. Evilginx is a red team / pentesting tool. Everything here was done against a domain and server i own, using a throwaway demo login and <strong>fake credentials</strong>. Phishing real people without written authorization is a crime, full stop. Don't be that person.</p>
</blockquote>
<h2 id="what-is-evilginx-and-why-2fa-doesnt-save-you"><a href="#what-is-evilginx-and-why-2fa-doesnt-save-you">What is Evilginx and why 2FA doesn't save you</a></h2>
<p>Evilginx is a <strong>man-in-the-middle reverse proxy</strong>. Instead of cloning a login page like old-school phishing kits (which never handle 2FA and break the moment the real site changes a class name), Evilginx sits <em>in between</em> the victim and the real website.</p>
<p>The victim talks to Evilginx, Evilginx talks to the real site, and it passes the traffic back and forth. Because it's a real proxy of the real site, the victim sees the genuine login page, the genuine 2FA prompt, everything. And here's the important bit: when the victim finishes logging in, the real site hands back the <strong>session cookies</strong>, the tokens that say "this browser is already authenticated." Evilginx grabs those on the way through.</p>
<p>Those tokens are issued <strong>after</strong> 2FA is already done. Import them into your own browser and you're in, no password, no second factor. That's the entire "2FA bypass". You're not defeating 2FA, you're stealing the thing that gets minted once 2FA is already complete.</p>

<h2 id="what-changed-since-the-2019-post"><a href="#what-changed-since-the-2019-post">What changed since the 2019 post</a></h2>
<p>If you read the old article, throw the muscle memory away. In v3:</p>
<ul>
<li><strong>Install:</strong> <code>go get github.com/kgretzky/evilginx2</code> is dead. You build it from source with <code>make</code>.</li>
<li><strong>DNS:</strong> Evilginx now runs its <strong>own built-in nameserver</strong> on port 53. In 2019 we added CNAME records per subdomain by hand. Now you delegate the domain (or use a wildcard) and Evilginx answers for everything.</li>
<li><strong>No bundled phishlets.</strong> The repo used to ship dozens of ready phishlets. For obvious abuse reasons those were removed. It now ships a single <code>example.yaml</code> template.</li>
<li><strong>Lures.</strong> Phishing URLs are "lures" now, managed objects with their own paths and settings.</li>
<li><strong>Anti-scanner protection.</strong> A blacklist system auto-bans crawlers hitting your domain, plus an "unauth" redirect that bounces randoms to a URL of your choice.</li>
</ul>
<p>Let's build it.</p>
<h2 id="step-1---the-environment-server--domain"><a href="#step-1---the-environment-server--domain">STEP 1 - The environment (server + domain)</a></h2>
<p>You need a server with a public IP and a domain name.</p>
<p>For the <strong>server</strong>, any cheap VPS works. In 2019 i used DigitalOcean, this time a small Vultr box, but anything is fine. I'm on a fresh <strong>Ubuntu 26.04</strong> instance with public IP <code>45.77.252.169</code>. Make sure ports <strong>80</strong>, <strong>443</strong> and <strong>53</strong> are reachable.</p>
<p>The <strong>domain</strong> part is where the old post is most outdated. Freenom is done, so no more free <code>.tk</code> domains. These days i use a cheap domain, or for quick lab work a dynamic-DNS provider. For this post i'm using <code>miarosoft.theworkpc.com</code> from <strong>Dynu</strong>, with a wildcard so every subdomain already points at the server:</p>

<h2 id="step-3---the-port-53-problem-fix-this-first"><a href="#step-3---the-port-53-problem-fix-this-first">STEP 3 - The port 53 problem (fix this first)</a></h2>
<p>Here's the first thing that'll bite you. Evilginx wants port <strong>53</strong> for its DNS server, but on modern Ubuntu <code>systemd-resolved</code> already owns it. Skip this and you get:</p>
<div class="eg-win"><div class="eg-bar"><span class="eg-dot" style="background:#e05f5f"></span><span class="eg-dot" style="background:#e0a44f"></span><span class="eg-dot" style="background:#4fe084"></span><span class="eg-title">nameserver bind failure</span></div><div class="eg-body"><div class="ln eg-err">[!!!] Failed to start nameserver on: :53</div></div></div>
<p>The fix: tell <code>systemd-resolved</code> to drop its stub listener, then point the system resolver at the real upstream config:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="bash" data-theme="github-dark-default"><code data-language="bash" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#FFA657">sudo</span><span style="color:#A5D6FF"> sed</span><span style="color:#79C0FF"> -i</span><span style="color:#A5D6FF"> 's/^#\?DNSStubListener=.*/DNSStubListener=no/'</span><span style="color:#A5D6FF"> /etc/systemd/resolved.conf</span></span>
<span data-line=""><span style="color:#FFA657">sudo</span><span style="color:#A5D6FF"> ln</span><span style="color:#79C0FF"> -sf</span><span style="color:#A5D6FF"> /run/systemd/resolve/resolv.conf</span><span style="color:#A5D6FF"> /etc/resolv.conf</span></span>

<div class="eg-win"><div class="eg-bar"><span class="eg-dot" style="background:#e05f5f"></span><span class="eg-dot" style="background:#e0a44f"></span><span class="eg-dot" style="background:#4fe084"></span><span class="eg-title">port 53 freed</span></div><div class="eg-body"><div class="ln"><span class="eg-p">$</span> sudo ss -tulpn | grep ':53 '</div><div class="ln eg-inf">(nothing, port is free)</div><div class="ln"><span class="eg-p">$</span> getent hosts github.com</div><div class="ln eg-w">20.205.243.166  github.com</div></div></div>
<p>Port 53 is free, DNS still works. Now Evilginx can grab it.</p>

<h2 id="step-5---dns-setup-this-got-way-easier"><a href="#step-5---dns-setup-this-got-way-easier">STEP 5 - DNS setup (this got way easier)</a></h2>
<p>In 2019 this was the annoying step: enable a phishlet, read off the subdomains it complained about, then hand-create a CNAME for each.</p>
<p>In v3 Evilginx runs its own authoritative nameserver, so the "proper" setup is to delegate the domain, register <code>ns1.&#x3C;domain></code> / <code>ns2.&#x3C;domain></code> glue pointing at your IP, then set the domain's NS records to those. After that Evilginx answers DNS for <strong>every</strong> subdomain automatically.</p>
<p><strong>But</strong> if you already have a wildcard <code>A</code> record on the box (like my Dynu setup), you don't even need that. The wildcard resolves every subdomain to the server already, so your DNS provider handles it and Evilginx's nameserver never has to be authoritative. Lazy, but works fine for a lab.</p>
<h2 id="step-6---phishlets"><a href="#step-6---phishlets">STEP 6 - Phishlets</a></h2>
<p>Phishlets are the heart of Evilginx. They're <strong>YAML</strong> files describing the target: which hosts to proxy, which cookies are the session tokens worth stealing, and how to spot the username/password in traffic.</p>
<p>Since nothing ships anymore, the bundled <code>example.yaml</code> is a great teaching template. It proxies <code>academy.breakdev.org</code> (Kuba's own Evilginx Academy, which is exactly why i'm using it, a safe author-provided demo target, not somebody's real login):</p>

<ul>
<li><strong><code>proxy_hosts</code></strong> - which subdomains of the target to proxy.</li>
<li><strong><code>sub_filters</code></strong> - string replacements applied to responses, this is how Evilginx rewrites the target's domain to yours inside HTML/JS so the victim never leaves your proxy.</li>
<li><strong><code>auth_tokens</code></strong> - the cookies you actually want, the session tokens that bypass 2FA.</li>
<li><strong><code>credentials</code></strong> - how to spot the username and password in POST data.</li>
</ul>
<p>For real targets you write your own phishlet or grab a community one, but be warned: real phishlets (Microsoft/Google/etc) <strong>break constantly</strong> because those providers change their login flow all the time. There's no bundled Microsoft phishlet, and the public ones rot fast. Writing and maintaining your own is the real skill. Kuba runs a paid <a href="https://academy.breakdev.org/evilginx-mastery">Evilginx Mastery</a> course on exactly that.</p>

<h3 id="a-note-on-the-tokens-the-actual-2fa-bypass"><a href="#a-note-on-the-tokens-the-actual-2fa-bypass">A note on the tokens (the actual 2FA bypass)</a></h3>
<p>You'll notice <code>tokens : empty</code> above. That's because i logged in with <strong>fake</strong> credentials, so the real site never authenticated me and never issued a session cookie. On purpose, i'm not compromising a real account for a blog demo.</p>
<p>In a real, authorized engagement this is the money shot: when the target enters genuine credentials <strong>and</strong> completes 2FA, the real site sends back the session cookies. Evilginx matches them against the <code>auth_tokens</code> list and stores them under <code>tokens</code>. You'd dump them with <code>tokens 1</code>, drop that JSON into a cookie-editor extension in your own browser, load the site, and you're logged in as the victim, no password, no 2FA challenge, because the cookie already represents a fully authenticated session. <strong>That</strong> is bypassing 2FA. You never broke the second factor, you just walked in with the pass it printed.</p>
<h2 id="step-10---the-new-defensive--opsec-features"><a href="#step-10---the-new-defensive--opsec-features">STEP 10 - The new defensive / opsec features</a></h2>
<p>A few v3 things that didn't exist in 2019:</p>
<ul>
<li><strong><code>blacklist</code></strong> - modes like <code>unauth</code> (ban anything hitting outside a valid lure), <code>all</code>, <code>off</code>. Keeps scanners out.</li>
<li><strong><code>config unauth_url &#x3C;url></code></strong> - where non-victims get redirected. Change it off the default rickroll.</li>
<li><strong>Redirectors</strong> - custom HTML landing pages (<code>redirectors/</code> folder) you attach to a lure, e.g. a fake "loading" splash before the real page.</li>
<li><strong>GoPhish integration</strong> - Evilginx can plug into GoPhish for campaign tracking, see the <code>gophish</code> fields in <code>config</code>.</li>
</ul>
<h2 id="conclusion"><a href="#conclusion">Conclusion</a></h2>
<p>Seven years on and the core idea hasn't changed: a reverse-proxy MITM sees everything the victim sees and grabs the post-auth session tokens that make 2FA irrelevant. What <em>has</em> changed is the tooling, v3 is cleaner, more capable and better-defended, and the whole install / DNS / cert dance is honestly nicer than the 2019 version once you get past the port 53 gotcha.</p>
<p>If you're on the blue side, the takeaway is uncomfortable but important: <strong>SMS and app-based 2FA do not stop this attack.</strong> The only real answer is phishing-resistant auth, FIDO2 / passkeys / hardware keys that are cryptographically bound to the real origin, so a proxy domain simply can't complete the handshake.</p>
<p>And once more, because it matters: only ever run this against systems you own or are explicitly authorized to test. Tear your lab down when you're done.</p>
